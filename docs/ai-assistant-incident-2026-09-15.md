# 企业版 AI 助手查询失败：2026-09-15

## 范围与结论

本机企业版测试环境，数据库 `coinimaging`，Gateway Log 57–59，台北时间 09:38–09:41。
三次应收查询均因参数错误及纠错失败终止。Odoo、网关与模型调用有正常响应。
这些日志不能证明所有类型的问题都失败，也不能用于判断另一台正式服务器的状态。

## 为什么会发生

| 层次 | 已确认的问题 | 影响 |
|---|---|---|
| 工具定义 | `analysis_mode` 是可选枚举，未说明趋势必须填 `trend`；执行器默认 `compare` | 本期日期明明有效，仍因没有基期日期失败 |
| 后端错误 | 本期和基期共用“期间必须提供日期”提示 | 模型无法判断应补模式还是补日期，重复原请求 |
| 日期条件 | schema 的 `value` 接受任意类型，执行器只接受二元素数组或单独的 `date_range` | 模型生成常见的 `value:{start,end}` 结构会被拒绝 |
| 汇总别名 | schema 只声明字符串；执行器实际要求英文标识符 | `alias:應收總額` 在数据库查询前失败 |
| 网关转换 | JSON Schema 转 Pydantic 时未保留 pattern、数字上下限及长度约束 | 即使以后补 schema 约束，原转换也会丢掉这类限制 |
| 纠错指令 | 原指令要求字段或查询错误先重新发现/描述；重复请求提示只引导重新查目录 | 参数格式问题被带回发现流程，随后触发重复查询停止 |
| 诊断日志 | 最终失败统一记录 `query_incomplete` | 实际原因藏在回复字段内的工具执行明细中 |

Log 57、58：缺少模式 → 默认 compare → 基期日期为空 → 重复参数 → 失败。

Log 59：缺少 model、未完成本轮发现/描述 → 日期范围结构错误 → 中文 alias 被拒绝 → 重复参数 → 失败。

已有测试大多直接构造正确参数，例如趋势测试显式给出 `analysis_mode=trend`，因此没有覆盖“模型漏填可选字段”的情况。
原有成功的单月查询也不能覆盖趋势、中文别名以及保留失败历史的对话。

## 修复

1. 工具 schema 明确模型参数、趋势/比较模式、基期要求及 alias 英文格式。别名可省略。
2. 无模式且无基期时，明确返回 `analysis_mode_required`，提示设置模式，保留已经提供的本期日期。
   兼容已有带基期的比较查询；比较缺少日期时指出 `baseline_start / baseline_end`。
   不根据问题关键词、月份分组或时间粒度自动推断业务口径。
3. 日期和数值范围兼容 `value:[start,end]`、`value:{start,end}`、`date_range:{start,end}`。
   同时传入矛盾范围时拒绝执行，避免静默选取错误范围。
4. 网关递归保留 schema 的 pattern、数值界限、字符串和数组长度限制，数组元素也覆盖。
   格式错误的反馈包含字段位置与所需约束，不输出被拒绝的输入值。
5. 格式错误直接纠正参数；只有未知模型、未知字段或明确的前置条件失败才重新查元数据。
   重复失败时重新给出具体错误，保持原有重复限制和整轮预算。
6. 最终失败日志保留最近尚未解决的工具错误码，并记录停止原因。
   用户提示不再要求用户为助手的参数格式错误补条件。
7. 真实重放发现趋势会漏掉客户账单条件，将应付等单据一起算入应收；补充通用“切换分析方式仍保留筛选条件”说明，明确既有财务定义同样适用于趋势与比较。
   这仍是业务定义及模型指令，未加入按问题关键词强制选表的代码。
8. 真实重放还发现“最近五个月”可能从四月算到九月，共六个月。统一相对月份说明：默认含本月至今日，起日往前 N−1 个月；明确要求完整月份才排除本月。结果增加实际返回时段数供模型核对。

版本标记：`2026-09-15.1`。未提高重试次数、查询上限或放宽证据和权限规则。

## 类似问题是否还可能出现

本次修复作用于通用查询接口，适用于其他日期范围、汇总和期间分析问题，不局限于应收。
跨层约束丢失和错误重试绕回发现流程已一并修复，并补入回归测试。

模型仍可能选择错误字段、错误日期口径或错误分组，也可能遗漏其他操作的必填参数。
权限和有效证据校验可以阻止部分错误结果进入答案，但不能证明自然语言理解始终正确。
采购、库存、关联查询等所有业务问题没有逐题做真实模型验收，不能宣称同类问题已完全消除。
本次真实样本只有一个公司币种且无负金额，没有以真实模型覆盖多公司、多币种或含负金额的绝对值口径。
趋势/比较筛选仍依赖模型按业务定义提交，本次成功不等于建立了可证明所有自然语言语义正确的校验器。
后续应保留失败会话做回归，并检查工具参数、执行证据和业务口径，不能只检查 HTTP 200 或日志状态 success。

## 后续：Log 66 跳过客户选择（2026-09-15.2）

台北时间 10:25:20，问题为“查某客戶最近訂單，請先讓我選擇客戶”。
助手先查询客户列表，随后自行取客户 ID 24262，再读取该客户两张大图订单并直接回答。
用户没有选择该客户。原有证据校验仅证明记录经过查询，不能证明客户是用户选定的。

仅补“先确认”指令仍不足：第一次真实重放虽然未查订单，却在重复客户查询后进入通用结束流程，
分页候选被错误当作未完成的全范围统计。该次重放判定失败，没有当成修复成功。

最终修复：

- `AgentStep` 增加结束本轮的 `select` 动作，引用当前成功客户搜索的 `candidate_evidence_id`；它不发起新的工具调用。
- 程序从已验证的 `display_name/name` 生成最多 5 个编号候选，返回 `clarification` 并停止规划，等待用户下一条消息。
- 单个候选仍等待确认，零个候选请用户提供关键字，部分候选明确说明不是完整名单。
- 保留普通 `tool` 和 `finish` 动作；不按用户问题关键词硬编码客户模型，不新增数据库字段，不创建选择记录。
- 通用交互说明明确：当前要求先选择时，历史对象或助手自己给出的对象不算用户选择。

验证：网关 47 项测试通过，其中候选终止覆盖零个、一个、分页候选、无效证据、失败证据及后续明确选择。

任何尝试查询后续资料或超过候选上限都会被拒绝并使验收失败，不会因为最后回答正确就算通过。

## B 工单有效总数被误称未完成（Log 69，2026-09-15.3）

原问题「B內部工單未完成數與明細」，Gateway Log 69，助手 Session 66，thread 3。
日志显示 search 和 aggregate 都只用了 `install_state != cancel`，回答「6750 笔未完成」。
`dtsc.makein.install_state` 的 `stock_in` 标签是「完成製作」；现有 `b_open` 指标及概览均排除 `stock_in` 和 `cancel`。
模型没有读取可选指标目录，只根据字段帮助中的“有效单据排除作废”生成条件，把有效总数误称未完成。

数据库只读核对：完成制作 6718、制作中 32、作废 1938；6750 是 6718 + 32。
再以用户 2 的 ORM 权限执行 `metric=b_open` 得到 32，前 5 条明细均为「製作中」。
thread 3 是清空后的新会话，只含这一问一答；旧 thread 1 已归档。此次错误不是从旧会话加载而来。

同题还有明细遗漏：首次引用 search 分页被完整性检查拒绝，模型改为 aggregate 后只引用总数证据，原先的明细未展示。

修复：

- `describe` 在同一响应中附上当前模型的已有 `metrics`。沿用 `business_metrics.json` 唯一口径，不复制状态映射或添加问题关键词路由；B/C/G/T 以及其他已有指标均适用。
- 指令明确匹配已有定义时优先用同一 metric 查数量和明细；一般查询仍可按用户明确范围执行。未完成、已完成和有效总数不能混称，不能只排除作废就叫未完成。
- 完成协议增加 `detail_evidence_ids`。总数仍引用完整汇总，分页明细独立展示，并验证其成功状态、模型及业务查询范围与汇总一致。失败、截断、不同范围的明细不能混入；页内数据仍不能证明全量总数。
- 运行时策略标记更新为 `2026-09-15.3`，预算不变。

验证：50 项 Gateway 测试、44 项内存查询测试及既有前端结果渲染检查通过。
新增覆盖 B/C/G/T 已完成和作废排除、元数据提供对应业务定义、其他显式有效总数查询不被改变、完整总数与分页明细同显、不同状态/模型/指标范围拒绝、失败证据拒绝。
