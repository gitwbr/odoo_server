### 清空当前对话（2026-09-15）

企业测试环境已加入：刷新页面，打开助手右上角「⋯」→「清空對話」并确认。成功提示「已開始新對話」后，旧问题、旧回答及旧查询资料不会再传给模型。旧会话采用归档方式保留；问答记录、Gateway 日志和业务资料不删除。

首次加载会建立空白会话，查询携带当前会话 ID。清空时归档当前登录身份全部 active 会话并创建新的空白会话；旧页面提交的客户选择、分页或重新查询会被拒绝并要求重新输入。前端忽略清空前迟到的历史及查询响应，清理旧结果按钮和输入草稿。遇到并发数据库冲突，由 Odoo 重新执行事务并再次核对会话，查询在模型调用前先刷新会话写入。正在执行的请求可能先完成，界面收到清空成功后才允许新查询。

清空入口是已登录用户的 POST 操作，启用 CSRF 校验及助手权限检查，目标身份由服务端确定；不作为模型工具开放。若无法确认清空成功，先重新读取当前会话，读取失败时不发送新查询。此操作不需要修改模型字段或升级模块。

## 当前实现

1. **动态发现数据来源。** 从当前用户可见菜单收集业务模型，再沿 Odoo 实际关系字段有界扩展。执行读取仍检查用户 ACL、字段权限及记录规则。不再限定印刷模块，也不再维护采购/库存/财务模型对允许列表。
2. **先核对字段再查数据。** Gateway 对带模型的请求先检查本轮动态发现结果，再检查是否成功 describe；缺失时返回 model_discovery_required/schema_required，不发出数据查询 HTTP 请求。集合来源、关系过滤的模型同样检查。由已有指标定义解析模型的 metric、服务端验证的 cursor 仍走执行器自身校验。
3. **结构化逐步执行。** 不再使用 create_agent 同时提供业务工具和最终答案工具。每轮模型只返回一个 AgentStep，程序按工具 schema 校验后执行；完成时 LLM 输出 query、catalog、clarification、conversation 或 failure，并引用本轮工具返回的 evidence ID。query 必须引用有效数据结果；字段目录、失败调用和历史结果不能冒充业务查询证据。后续失败不能被前面的成功结果掩盖。
4. **通用纠错与停止。** 字段错误、缺少证据或完成协议不合法时，在同一轮剩余超时预算内纠正。runtime_policy.json 中 max_steps 统一限制规划步数；成功的相同请求不会重跑，失败请求只有获得新元数据后才允许同参数重试。重复请求或步数用尽后调用只允许输出 TurnAnswer 的完成阶段，不再执行查询。失败保持失败，详细过程进 AI Gateway Log；用户不再看到根据错误字符串拼出的“安全限制”解释。口径不明可以明确澄清，不编造数值。
5. **回答与日志分离。** 全部工具调用及完成验证事件保留在日志；回答区仅展示最后引用的有效结果。澄清不附带旧的或失败的结果。日志沿用既有“回复”字段，不迁移历史记录。
6. **关联条件显式化。** 通用集合/关系查询不再根据模型名自动排除作废状态。要查有效单据，由模型核对真实状态字段后显式给出条件，或选用有明确说明的业务指标。

语义理解仍由 LLM 完成；执行证据校验能阻止无查询/失败结果被用作数据完成证据，但不能证明模型对每一个自然语言问题的业务理解都正确。因此歧义澄清和财务报表核对仍必要，不能宣称仅靠协议消除了所有语义错误。

金额单位补充（2026-09-11）：describe 现在返回 Monetary 字段真实的 currency_field；普通汇总与期间分析共用同一单位校验。金额计算必须按其币种字段分组，或以顶层 AND 过滤固定单一币种；计数不受此限制。不指定 account.move 或 currency_id 等业务名称，不自动替用户选择币种。必要理由：不同币种不能直接相加或比较；元数据不足时明确失败，规则位于通用执行器 `_validate_measure_currencies`。

## 已删除的旧机制

- `_BUSINESS_EDGES` 固定业务模型对、`dtsc.menu_root` 固定菜单根及 `_module == dtsc` 扩展条件。
- `_requires_query` 中英文问题关键词及例外词判断。
- “我能查什么”等自然语言的精确匹配执行分支。UI 明确提交的翻页/重新查询请求继续执行已选条件，不是自然语言路由。
- 根据“安全规则排除”“Traceback”等字符串过滤用户答案的补丁。
- 旧版 `_local_query`、订单号/关键词/状态/订单类型解析、固定订单搜索与详情工具定义及回调分支。它们不再作为备用路径残留在服务中。
- 通用关系查询对特定 B/C/G/T/S 模型自动追加 cancel 过滤。
- 把“附件、图片、签名”等普通字段名称一律作为敏感字段的关键词拦截；文件本体能力限制仍保留。

历史会话中已有的旧订单卡片仍由前端兼容展示。这只读取历史展示数据，不重新启用旧查询工具，也不据此生成新的业务答案。

## 必须保留的固定规则及理由

| 编号 | 当前规则 | 为什么必须有 | 适用范围与退出条件 |
|---|---|---|---|
| S01 | 只读工具、内部用户、当前用户 ACL/字段/记录规则 | LLM 不能授予读取或写入权限。能发现关系不意味着能读目标数据 | 所有查询；不移除，也不能以 sudo 扩大业务结果 |
| S02 | 整表排除 `dtsc.vatlogin` | 不仅存密码，普通字段 search_line 还拼接了密码；仅凭字段名和 Odoo 读取权限无法阻止把凭证发送给模型 | 账号表；提供经验证的不含凭证及派生凭证的投影后才能缩小封锁 |
| S03 | 排除助手/Gateway 内部模型前缀，以及 ir/mail/bus/auth/base/web/res.config/res.users 技术模型族 | 扩大动态发现后，关系可通向配置、用户凭证、系统消息、跨会话日志。后台有权阅读不等于适合发给 LLM | 集中 JSON 明列前缀；若某个技术模型确有业务用途，先建立经过审核的安全投影再替换对应例外，不靠增加业务关联白名单解决 |
| S04 | 密码、Token、Secret、API Key 等凭证语义字段排除 | Odoo 字段元数据未统一标记“可发送给外部模型”；即使管理员有读权限也不能直接把配置密钥发出去 | 集中关键词配置，仍检查名称、标签、help；这是保守保护，可能误挡。建立可靠敏感属性/派生关系标注后替代，不能直接删保护 |
| S05 | binary、html 不进入通用返回字段 | 当前查询工具没有文件读取、HTML 内容处理协议，直接读取会超出能力与上下文边界 | 文件本体/HTML；专用解析能力具备权限及大小处理后单独开放。普通附件数量、文件名不因名称直接封锁 |
| T01 | 操作、过滤运算符、字段类型、聚合语法有限集合 | 执行器必须定义合法语法，不能接受任意 SQL/方法调用。这不是业务选表规则 | 工具 schema 与执行校验；扩展操作需要对应执行实现和测试 |
| T02 | 分页、关联条数、条件深度、发现层数、响应长度及历史长度上限 | 防止无界遍历、循环、过大响应和失控查询；不能返回部分数据却声称精确总量 | query_policy.json 集中预算；数值可调整，调整需负载与截断回归，不移除有界性 |
| T03 | 超时、推理步数与纠错次数 | 防止模型无限调用，保障请求及时结束 | runtime_policy.json；共用整轮剩余时间。schemas 仅校验可接受范围，不能让请求任意提高上限 |
| T04 | 游标签名、身份/公司绑定、有效期、数据变化校验 | 防篡改、跨用户复用及过期翻页 | 签名和权限校验保留；TTL/页数上限为集中配置 |
| B01 | 命名指标的状态/分母/日期等明确业务定义 | 元数据只能说明字段存在，无法证明“有效”“完成”“应收”应该怎么算，不能让 LLM 猜业务政策 | business_metrics.json 中可选定义；不是强制动作，也不禁止未定义问题。业务口径变化只改目录，不改通用执行器 |
| B02 | A/F/E/M/D、B/C/G/T、S 的项目事实 | 用户明确指定，不能删除后让模型重新猜；B/G 需求重叠与母单去重会影响结果 | business_context.md；保留事实，运行时仍核对技术字段 |
| B03 | 日常应收／应付总额采用 DTSC 账单业务金额定义 | Log 39 使用标准发票金额，与界面业务税额算法不同。字段名称和类型不足以推导采用哪套税额规则，因此必须向 LLM 提供已核对的业务事实 | 唯一运行时事实源为 business_context.md 的财务段；这是显式业务定义，不是关键词路由或强制选表代码。仍动态发现并验证，用户明确指定其他口径优先。公司币种、逐笔绝对值、日期及状态范围一并说明；将来账单口径修改时同步维护该段 |
| B04 | 采购采用 DTSC 自定义状态 | models.py 的 PurchaseOrder 与概览 _get_purchase_metrics 使用 my_state；Odoo 标准 receipt_status 的待收货范围不同 | business_metrics.json 定义已确认采购与待收货采购，describe 自动提供。询价单不计入已确认采购；按 date_order 归属期间。未增加按问题关键词选模型的执行分支 |
| B05 | 客户／供应商身份沿用 rank 条件 | res_partner.py 的两个显示勾选由 customer_rank / supplier_rank > 0 计算，本身没有搜索方法；is_company、active 不能代表客户或供应商 | business_context.md 明示该事实，仍经 describe 验证字段。通用执行器按字段元数据拒绝不可搜索的条件，不按问题文字固定查询分支 |

`dtsc.linebot`、`dtsc.interoperate`、`dtsc.ai.check.log` 已从整表拒绝列表移除。它们是否被发现仍取决于菜单/关系及权限；凭证字段和文件本体继续受上述规则约束。这里没有承诺可以读取任意日志或配置字段。

## 当前预算与能力边界

查询默认 20、每页最多 100；返回字段最多 20；分组最多 3、度量最多 5；关联集合最多 5000；发现关系最多 4 层、扩展目录受 500 模型预算约束；趋势最多 60 段、1096 天。实际值以集中 JSON 为准，本段是说明，不作为第二份执行配置。

图表数量、收藏上限和 CSV 格式属于前端显示协议，不参与模型选择或权限判断。CSV 仍只导出当前结果。历史卡片/分页原样查询需要兼容，因此没有删除其数据格式。

2. **条件被静默忽略。** aggregate 接受了不适用的期间参数，却未将其转成日期条件；is_supplier / is_customer 等不可搜索计算字段也会被 Odoo 忽略。现在提前拒绝不适用期间参数及无搜索方法的非存储字段；describe 提供 searchable 元数据，并引导保留业务身份、日期范围后修正。还明确指标识别码不是 measures.field，避免错误修复时丢掉日期。
3. **统计与明细误判为不同范围。** metric 与普通 search 的参数写法不同，即使实际条件相同也曾导致完成校验失败。现在使用实际执行模型、规范化条件、用户／公司／时区生成范围指纹，纯 AND 的顺序及重复条件不影响比对，OR/NOT 保守保留。已有完整统计时，纠错只指导重新引用现有统计和明细证据，不要求重复查询。
4. **选择流程没有真实记录或遗失 ID。** 模型曾将 discover 的模型目录当作候选；之后又因为历史只留下显示名称，把选项 4 / 3 当作数据库 ID。现在在查到真实候选前，步骤 schema 不开放 select；服务器生成有序 universal_selection 上下文，沿用现有 result_json 保存，不另建记忆库，也不展示内部 ID 表格。纯编号回复只按紧邻的选择回合解析为实际 record_id，并保留原查询要求；清空对话后不会继承该映射。
5. **空结果、缺失答复及状态目录问题。** 空 SQL sum 现在返回 0，平均值等无定义统计保留空值；finish 必须包含结构化答复；G 指标按模型实际的 succ / cancel 状态校正，移除不存在的 stock_in。当前时间同时提供日期、带时区时间，逾期不能被替换成“早于今天零点”。
6. **正确数据被自由文字写错。** 供应商分组数据正确合计 21 单，模型曾写成 16；查询到 2 张采购单时，也曾写“最近 5 张”并编造 yourdomain.com 链接。完整分组的总笔数由执行器提供，分组说明及纯记录列表说明由服务器根据真实结果生成；单据链接仍由现有界面生成，避免自由文字重新计算或拼接网址。
