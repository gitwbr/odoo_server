# AI 助手通用查询需求

## 目标

在现有企业版 AI 助手中提供一个通用查询工具，让 AI 能够自行发现并查询「印刷订单系统」内的 Odoo 模型与字段，完成资料查找、统计、分组、排行、趋势和比较分析。

此功能只用于查询和分析，不建立、修改或删除业务资料。

## 查询方式

- 使用 Odoo 模型和 ORM 查询资料，不让 AI 直接查询 PostgreSQL 表或执行 SQL。
- AI 先寻找与问题有关的 Odoo 模型，再读取模型字段说明，最后执行查询或统计。
- 查询结果由 AI 整理成容易理解的繁体中文回答。
- 使用一个通用查询工具，不为每个模型或每种问题分别建立工具或 API。

## 通用工具能力

同一个通用工具应支持以下操作：

- `discover`：依业务关键词寻找相关模型。
- `describe`：取得模型说明、字段名称、字段类型、字段说明、选项值及关联模型。
- `search`：依条件查询明细，并支持选择字段、排序和限制笔数。
- `aggregate`：执行计数、加总、分组、排行及日期趋势统计。
- `count_distinct`：依关联字段去重计数，例如按 `checkout_id` 统计母单数量。

AI 可以在同一轮问题中多次调用这个工具，组合不同模型的查询结果后再回答。

## 印刷订单系统范围

通用工具只发现和查询印刷订单系统相关模型：

- 第一版通用工具只开放给内部用户与系统管理员；商城会员和统编客户继续使用既有的受限大图订单查询。
- 自动纳入当前内部用户可见的「印刷订单系统」根菜单 `dtsc.menu_root` 下，窗口 Action 实际打开的模型，以及 Server Action 明确绑定的模型；只读取 Server Action 的绑定模型，不执行其代码。
- 自动纳入上述入口模型一层关系可达、由 `dtsc` 模块定义的持久业务模型。
- 不自动纳入所有 `dtsc.*`，并以极小的模型级排除清单排除已知凭证、认证、设置和 AI 日志模型，例如 `dtsc.vatlogin`、`dtsc.linebot`、`dtsc.interoperate`；被排除模型不得通过关系再次进入范围。
- 允许从已纳入模型的关系字段理解相关资料，但不得借此无限扩展到整个 Odoo 的技术模型。
- 不查询未被印刷订单系统使用的 Odoo 原生模块和技术资料。
- 实际可查询资料仍依当前登入用户在 Odoo 中的权限与可见范围决定。

## 模型与字段说明

通用工具应自动读取 Odoo 已有的模型与字段元数据，包括：

- 模型 `_description`。
- 字段 `string` 和 `help`。
- 字段类型。
- Selection 选项及显示名称。
- Many2one、One2many、Many2many 的关联模型。
- 字段是否为存储字段或计算字段。

说明补充原则：

- Odoo 原生字段未改变用途时，不需要重新描述。
- 自定义模型应有清楚的 `_description`。
- 自定义新增字段如果现有 `string` 已经清楚，不需要重复补充。
- 自定义新增或修改后的字段若名称与实际用途不容易理解，应补充 `help`。
- 状态、日期、金额、数量、才数和关联字段如果存在特殊口径，应优先说明清楚。
- 不另外维护一份完整的模型、字段或业务别名清单。

## 业务关系说明

- A：普通大图订单主单，模型为 `dtsc.checkout`。
- F：打样单，属于 `dtsc.checkout`，由 `is_dayang=True` 将 A 单号改为 F。
- E：重制单，属于 `dtsc.checkout`，由原订单指定产品行复制生成，并保留 `source_name`。
- M：被合并单标记，属于 `dtsc.checkout`；它是被合并的非目标 A 单，不是合并目标单。产品行移至目标订单，并以产品行上的 `origin_checkout_id` 保留原订单关系。
- D：CRM／报价相关生成的大图订单，属于 `dtsc.checkout`。
- B：内部工单，模型为 `dtsc.makein`。
- C：委外工单，模型为 `dtsc.makeout`。
- G：代工单，模型为 `dtsc.makeom`。
- T：施工工单，模型为 `dtsc.installproduct`。
- B、C、G、T 通过 `checkout_id` 与大图订单母单关联。
- 产品行制作方式为 `make_in` 或 `make_om` 时进入 B，`make_out` 时进入 C，`make_om` 时同时进入 G；`is_install=True` 时进入 T。B/C/G 生成时会跳过 `can_be_expensed=True` 的产品行。
- `make_om` 产品行同时属于 B 内部工单需求与 G 代工单需求；统计 B、G 需求时允许重叠。单一模型的母单数量可按 `checkout_id` 去重；跨 B/G 等多个模型统计母单联集时，不得把各模型的去重结果直接相加。
- S：出货单，模型为 `dtsc.deliveryorder`，通过 `checkout_ids` 关联一张或多张大图订单。
- S 是独立单据，不是大图订单状态；作废 S 后 `checkout_ids` 历史关系可能仍保留，有效 S 默认排除 `install_state=cancel`，目前有效单号可再核对大图订单 `delivery_order`。
- `dtsc.checkout.estimated_date` 是目前排定或选择的发货时间；未生成 S 时用于大图订单超期未出货判断，生成 S 时同步到 `dtsc.deliveryorder.delivery_date`，但不代表已经完成出货。大图订单逾期与出货单逾期应分别依各自口径统计。
- B/C/G/T 的有效单据统计默认排除 `install_state=cancel`。

## 查询限制

- 第一阶段只允许读取，不允许创建、修改、删除、付款、上传或自动执行业务动作。
- 所有明细查询必须限制返回笔数。
- 大量资料优先使用 ORM 聚合，只把必要结果交给 AI。
- 默认不返回图片、附件、Binary、HTML、密码、Token、API Key 或其他敏感及大型字段。
- 模型级排除优先于字段过滤，避免名称不敏感但实际拼接密码或 Token 的计算字段间接泄漏内容。
- 非存储计算字段不直接用于一般聚合；需要时应改查可聚合的来源字段或使用明确业务口径。
- AI 不得自行编造不存在的模型、字段、状态或查询结果。

## 预期查询类型

通用工具应优先覆盖以下问题：

- 指定条件的订单、工单、出货、客户、产品、采购、库存或账单明细。
- 数量、金额、才数等合计。
- 按客户、业务员、状态、订单类型、产品、机台或日期分组。
- 排行、日期趋势及不同时段比较。
- 通过关联字段统计下游单据数量或去重后的母单数量。

无法只从模型结构判断的复杂口径，应依据已确认的业务关系说明处理；后续若发现通用工具无法稳定回答，再针对该业务口径补充说明或专用计算逻辑。
